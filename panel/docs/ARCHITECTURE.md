# NivCreative Panel – Architecture

A standalone PHP 8.1+ / MySQL application (no framework, no Composer, no build step required to run) that lives in
`/public_html/panel` and works from either `https://nivcreative.com/panel` or a sub-domain root. The base path is detected
from `SCRIPT_NAME`, so no URL is hard-coded.

## Layout

```
index.php                 front controller
.htaccess                 routing + blocks src/ config/ storage/ ... + no public caching
src/
  autoload.php            PSR-4 autoloader (Nivc\)
  routes.php              every route + its middleware flags (auth | admin | client | public | selfcsrf)
  Core/                   Config, App, Router, Request/Response, Session, Auth, Actor, Csrf, Crypto, RateLimiter,
                          Validator, I18n, View, Db, Logger, NowTime, HttpException
  Services/               business logic (one class per area): ClientService, WebsiteService, LandingPageService,
                          LeadService, AnalyticsService, TrackingService, BillingService, NotificationService,
                          MaintenanceService, DashboardService, Settings, Phone, Domain, Csv, UrlGuard, ApiLog, Paginator
  Controllers/
    Api/                  thin JSON controllers (ClientsApi, LeadsApi, WebsitesApi, LandingPagesApi, MiscApi, IngestApi)
    Web/                  AuthController, PageController (app shell), InstallController
views/                    PHP templates (layouts/app, layouts/auth, auth/*, partials/icons)
lang/                     he.php + en.php (GENERATED from tools/i18n_table.py — edit the table)
assets/                   css/app.css, js/core.js (UI library), js/charts.js (SVG charts), js/pages/*.js (one per screen),
                          js/lead-drawer.js, js/tracker.js (public view tracker), js/auth.js, img/
database/schema.sql       fresh-install schema; database/migrations/ for later changes (bin/migrate.php)
bin/                      install.php, migrate.php, cron.php, seed-demo.php (dev only)

tests/                    unit.php, e2e.php (security + functional matrix), router.php (php -S router)

```

## Request flow

1. `App::handle()` matches the route, starts the session (not for `public` ingest routes), restores "remember me",
   resolves the locale (user preference → cookie → default `he`).
2. Middleware flags are enforced in `App`: `auth` (401 JSON / redirect to login), `admin` (403), `client` (admins are
   redirected to `/admin`). All state-changing requests need a CSRF token (`X-CSRF-Token` header or `_csrf` field);
   login/forgot/reset verify it themselves (`selfcsrf`) to show a friendly message.
3. Controllers call a service. **Every sensitive controller method also calls `Base::admin()` / `Base::actor()`** — role
   checks do not rely on routing alone (defence in depth).
4. Pages are an application shell + a JSON boot payload (`<script type="application/json" id="boot">`, CSP-safe).
   Data is always fetched from the authorised API; no client data is embedded in HTML.

## Tenant isolation (the most important rule)

`Actor` (built from the session on every request) is the only source of truth:

* `Actor::scopeClientId($requested)` — clients are **always** pinned to their own `client_id`; whatever `client_id`,
  `website_id` or `landing_page_id` the request carries is combined with `AND client_id = <own>` in SQL, so foreign IDs
  simply match nothing. Admins may pass a `client_id` (or none = all).
* `Actor::assertOwns($ownerClientId)` — single-resource lookups (lead, website, landing page) throw **404** (never 403,
  so existence is not revealed) when the row belongs to another client.
* Lead ingestion takes `client_id` from the authenticated **website row**; a `client_id` in the payload must match or the
  request is rejected (403).

`tests/e2e.php` exercises these rules against a running server (cross-tenant GET/PUT/notes/contact/export/analytics/filters).

## Data model

`clients` (tenants, `public_id` = unique internal `client_id`) → `users` (login accounts) · `subscriptions` (billing history; the
current one has the latest `end_date`) · `websites` (one client → many; `site_key` public + `token_hash` secret + optional
encrypted WP credentials) → `landing_pages` (one website → many; `path_key` for tracking) → `leads` → `lead_notes`,
`lead_activity`. `page_views` aggregates one row per (landing page, day, anonymous visitor). `notifications`, `settings`,
`api_logs`, `rate_limits`, `remember_tokens`, `password_resets`.

All `DATETIME` values are stored in the site timezone (`Asia/Jerusalem` by default) so `DATE()`/range queries match what
users see without relying on MySQL timezone tables (which shared hosting often lacks). Indexes cover `client_id`,
`website_id`, `landing_page_id`, `status`, `created_at`, `utm_source`, and the composite lookups used by dashboards.
Lists are always paginated (`per_page` ≤ 100); CSV export streams in chunks of 1000.

## Metric definitions

* **Page view** = a *visit* to a landing page. A refresh by the same visitor within 30 minutes is not a new visit.
* **Unique visitors** = distinct anonymous visitor hashes (HMAC of the tracker's random id with the app key; no IP, no cookie
  on the server side).
* **Conversion rate** = leads ÷ page views × 100.
* **Closed deals / revenue (client)** = leads with status `closed` whose `closed_at` falls in the range / sum of `deal_value`.
* **Revenue (admin)** = sum of *paid* subscription amounts (what NivCreative billed), by `start_date`.
* **Funnel** = leads created in the range grouped by their *current* status stage (contacted ⊂ meetings ⊂ closed).
* **Lead aging** = `new` for ≥ 2 h (warning) / ≥ 24 h (late); other open leads with no activity for 3 days = stale.
* **Account status** = disabled › expired (end date passed) › expiring (≤ 30 days) › active.

## Notifications

Stored as *type + params* (not text) and translated when read, so every user sees their own language. `MaintenanceService`
(cron every 10 min via `bin/cron.php`; also throttled on dashboard loads) creates deduplicated notifications for expiring/expired
subscriptions, waiting leads, silent websites and lead spikes. `NotificationService::registerChannel()` is the extension point
for e-mail / WhatsApp / SMS / Telegram / push.

## i18n

No UI string is hard-coded. PHP uses `t('key', ['param' => …])`, JS uses `NC.t(...)` with the full dictionary delivered in the
boot payload. `tools/build_lang.py` generates `lang/he.php` and `lang/en.php` from one table and fails if code references a missing
key. `<html dir>` follows the locale (rtl for `he`), CSS uses logical properties, charts keep a left-to-right time axis, phone
numbers/URLs/e-mails are isolated as LTR runs. The choice is saved on the user and mirrored in the `nivc_lang` cookie for the login page.

## Payments

No gateway yet. `BillingService::addSubscription()/extend()/updateSubscription()` are the only writers of subscription rows, so a
gateway webhook can later call them without touching the UI.
